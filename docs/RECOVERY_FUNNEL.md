# 회수 입구 재설계 기록

`underbody_mission_02`는 전개·60초 견인을 마쳤지만 회수 중 71.114932초에 최소 간격 한도로 중단됐다. 포획은 이루어지지 않았고 문도 열린 상태다. 마지막 핀 충돌 이전부터 센서 코가 출구 바닥의 수직 면에 막혀 있었다. 70.2초의 접촉 법선은 후방을 향했고, 동체와 출구 프레임이 같은 부근에서 반력을 냈다. 윈치가 계속 감으면서 장력이 최대 34.644638N까지 증가한 뒤 센서가 풀려 들어갔다. 이 값은 입력 장력 한도 8N을 넘는다.

단면과 접촉 쌍은 `test_models/H1_reference/runs/entry_redesign_diagnosis`에 보존했다. 마지막 충돌 장면만 보고 핀 크기나 포획 허용치를 바꾸지 않았다.

## 변경한 형상

최종 개발 형상은 `examples/h1_recovery_funnel_v2.yaml`과 `test_models/H1_reference/geometry_variants/normal_r3_recovery_funnel_v2`다.

- 입구 56×70mm를 80×120mm로 확장했다. 바닥은 40mm 낮추고 천장은 10mm 올렸다.
- 직사각 프레임, 상자형 가이드, 별도 경사 블록을 제거했다. 입구에서 50×50mm 목 부분까지 이어지는 두께 2mm의 경사 통로로 교체했다.
- 동체 외피도 같은 통로에 맞춰 절삭했다. 통로 내부와 남은 외피의 CAD 교차 체적은 0mm³다.
- 도어를 152×80×2mm로 늘렸다. 270° 접힘을 유지하면서 힌지 지지부와 접힘 받침을 새 통로에 연결했다.
- 센서 형상·질량·관성, 포획 위치·속도·각도 조건, 접촉 강성·감쇠·최소 간격은 유지했다.

통로 밀도는 **가정값 1200kg/m³**다. 기존 제거 부품의 질량을 빼고 절삭 체적과 도어·지지부 변경을 반영했다. 건조 기체 질량은 2.330784kg에서 2.395751kg으로 64.967g 늘었다. 무게중심과 관성도 CAD로 다시 계산했다. 구체적인 질량 증감과 좌표 변환은 `geometry.json`에 있다. 도어 질량은 기존 모델과 같이 닫힌 자세에서 기체 강체에 포함된다. 도어 서보와 움직이는 문 자체의 관성 결합은 해석하지 않는다.

v1은 개발 중간 형상이다. 통로 입구의 외피 절삭과 지지부 연결을 수정한 v2로 대체했으며, `funnel_recovery_01`은 의도적으로 중단했다. 회수 성공의 근거로 사용하지 않는다.

## 확인한 항목

`runs/funnel_door_v2/audit.json`의 도어 0~270° 각도 271개 표본에서 체적 겹침과 CAD 오류가 없었다. 별도 `continuous_sweep.json`에서는 0.1° 간격의 2701개 자세와 각도 사이의 최대 이동량을 함께 계산했다. CAD 거리에서 이동량과 수치 여유를 뺀 최솟값은 약 0.069mm로, 가정한 강체 형상의 0~270° 전 구간에서 양수였다. 제작 공차나 부품 변형을 고려한 여유로 해석하지 않는다.

실제 flow5 7.57 VLM2로 만든 정밀 공력표 `runs/underbody_aero_refined_01/aero_database.npz`를 사용한다. 주익과 꼬리날개 형상은 같다. 새 무게중심의 모멘트는 기존 공력 기준점에서 변환한다. `runs/funnel_aero_v2`에서 변경된 수납 트림 근처를 실제 flow5로 다시 계산했다. 직접 계산과 보간의 최대 힘 차이는 약 0.00290N, 모멘트 차이는 약 0.00207Nm로 설정한 0.05N·0.02Nm 이내였다. 새 입구 주변 유동을 flow5로 계산했다는 뜻은 아니다.

`tests/test_recovery_funnel.py`의 9개 검사를 통과했다. 도어 CAD와 충돌 형상의 좌표 일치, 질량 증감, 유지한 형상과 포획 조건, 기존 70.2초 막힘 자세에서 새 입구의 여유를 확인한다. 마지막 검사는 동일 자세의 형상 비교이며 변경 후 운동의 성공을 뜻하지 않는다.

## 회수 재계산

`runs/funnel_recovery_02`는 첫 센서 접촉 이전인 기존 69.8초 저장 상태에서 시작한다. 실제 위치·속도·자세를 가져오고 질량 중심 기준점만 변환한다. 두 견인점의 물리 위치·속도가 보존되는지 검사한다. 새 형상으로 처음부터 전개한 비행과 구분한다.

```powershell
.\.venv\Scripts\python.exe test_models/H1_reference/run_underbody_mission.py --case examples/h1_recovery_funnel_v2.yaml --out test_models/H1_reference/runs/funnel_recovery_NEW --aero test_models/H1_reference/runs/underbody_aero_refined_01/aero_database.npz --trim-validation test_models/H1_reference/runs/funnel_aero_v2/trim_validation.json --audit test_models/H1_reference/runs/funnel_door_v2/audit.json --recovery-reference test_models/H1_reference/runs/underbody_mission_02/complete --recovery-start 69.8
```

포획이 실제로 감지된 경우에만 안정화, 내부 줄 정리, 문 닫힘으로 넘어간다. 단계 사이 상태를 덮어쓰지 않는다. `pipeline.json`이 `completed`이고, `complete/summary.json`의 포획·최종 도어 각도와 CAD 검사를 확인한 뒤에 회수 완료로 판단한다. 접촉 중단·한도 초과는 별도로 보고한다.

새 수납 트림에서 전 과정을 계산하려면 위 명령에서 `--recovery-reference`, `--recovery-start`를 빼고, 기존 회수 명령만 쓰도록 `--command-reference test_models/H1_reference/runs/underbody_recovery_03/case.yaml`을 지정한다. 완전 전개 길이 2.7m와 유지 60초는 그대로다.

`runs/funnel_mission_01`에 이 전 과정 계산을 별도로 시작했다. `finish_underbody_mission.py`가 실행 시간 한도로 끝난 경우에는 입력·상태 일치를 확인하고 이어 계산한다. 물리·수치 실패는 자동으로 넘기지 않는다. 실행을 시작했다는 기록과 전체 임무 완료 판정은 구분하며, 최종 판정은 해당 폴더의 `completion_status.json`과 `complete/verification.json`을 확인한다.

회수 구간 시험에서는 73.532269초에 포획을 감지했고, 이후 0.3초 안정화도 완료했다. 이때 남은 회수 길이는 약 0.145mm였다. 기존 후처리 명령은 항상 0.25m/s까지 가속하려 했기 때문에 필요한 가감속 거리가 부족하다는 오류로 멈췄다. 물리 적분 실패나 새 형상 간섭에 따른 중단은 아니었다.

`cleanup_schedule`은 이처럼 남은 길이가 짧으면 원래 예정된 최종 감속 이력을 그대로 유지하도록 수정했다. 이미 모두 감긴 경우에는 줄 길이를 유지하고 문 닫힘만 예약한다. 기존 충분한 길이의 가속 정리 방식은 유지한다. `tests/test_cleanup_command.py`에서 수정 전후의 과거 입력 보존, 실제 짧은 잔여 길이에서 원래 감속 명령 보존, 회수 완료 뒤 문 닫힘 순서를 확인한다.

`runs/funnel_recovery_03`은 완료된 `funnel_recovery_02/settling`의 최종 상태와 동일한 해석 코드·형상·공력표를 확인하고 문 닫힘까지 이어 계산한다. 이전 회수·안정화 결과도 그대로 연결하며, `funnel_recovery_02`의 오류 기록은 보존한다. 전체 임무의 완료 처리에도 이 특정 명령 생성 오류만 같은 검사를 거쳐 처리하도록 반영했다. 다른 물리·수치 오류를 자동으로 재시도하지 않는다.

`funnel_recovery_03/complete/verification.json`에서 **69.8~75.213885초 회수 구간의 완료를 확인했다.** 포획은 73.532269초, 최종 문 각도는 0°였다. 총 54,803개 저장 상태의 연결 지점에서 위치·속도·자세·와이어 상태가 정확히 이어졌고, 총질량도 일정했다. 선택한 211개 CAD 자세에서 겹침과 질의 오류는 없었다. 최대 장력은 1.242388N, 최대 윈치 토크는 0.018636N·m였으며 입력된 한도의 초과 항목은 없었다. 최대 접촉력 6.016663N은 미검증 접촉 물성을 사용한 계산값이다.

완료 판정은 `verified_completed_window`다. 새 형상의 수납·전개·60초 견인을 포함한 전체 임무 완료, 분할·시간 간격 수렴, 실제 기체 검증을 뜻하지 않는다. `funnel_mission_01`은 3.995614566초에서 수치 정체로 중단됐다. 해당 결과와 원래 오류 기록을 보존했다. 후처리만 복구해 0~3.9956초의 실제 재생과 CAD 검사 결과를 저장했으며, 완료 영상으로 표시하지 않는다.

재현용 빌더는 `build_recovery_funnel.py`다. 기존 형상·결과를 덮어쓰지 않으므로 새 버전 이름을 사용한다. 형상 단면 비교 화면은 `runs/entry_redesign_report/report.html`에 있으며 실제 계산 재생과 구분해서 표시한다.

통로와 지지부는 동체에 강체로 고정된 것으로 계산한다. 통로와 외피 사이의 조립 여유를 연결하는 접착·체결부 상세와 그 유연성은 모델에 포함하지 않았다. 국소 후류, 문·통로 추가 항력, 접촉 물성, 재료 강도, 제작 공차, 케이블 분할·시간 간격 수렴은 아직 검증하지 않았다. 형상 변경이 실제 기체의 회수 안전성을 입증했다는 판정은 시험 비교 전에는 하지 않는다.

## 계산 자원

현재 PC는 물리 코어 8개, 논리 프로세서 16개다. 사용자 요청에 따라 H1 계산의 CPU 사용 범위를 논리 프로세서 0~11로 제한했다. 12~15는 이 계산에서 사용하지 않는다. 운영체제나 다른 프로그램의 CPU 사용을 제한하는 설정은 아니다.

`test_models/H1_reference/compute_resources.json`에 자원 설정을 저장했다. 초기에는 회수·전체 임무 해석 두 개를 함께 실행했다. CAD 검사는 전체 작업을 합쳐 최대 10개 프로세스가 동시에 수행하며, 여러 검사 작업이 겹쳐도 공유 작업 한도를 적용한다. 각 검사 시작 시 사용 가능한 메모리와 궤적 크기를 확인해 작업자 수를 줄일 수 있다. 실제 선택한 수는 결과 폴더의 `compute_resources.json`에 남긴다. 이 설정은 검사 명령의 기존 `--workers` 값보다 우선한다. 새 전체 임무는 적분을 마친 뒤 CAD 검사로 넘어간다.

입구 통과 구간의 67개 자세 검사는 작업자 7개, 완료 궤적의 211개 자세 검사는 작업자 3개로 실행했다. 후자는 당시 메모리 여유와 더 큰 궤적 배열을 반영한 수다. CPU 사용 범위와 공유 작업 한도는 실제 Windows 프로세스를 생성해 검사했다. 관련 자원·정리 명령·형상 검사 13개가 통과했다.

초기 자원 배분은 CAD 검사만 병렬화했다. 이후 `parallel_rhs.py`를 추가해 Radau가 요구하는 서로 독립적인 수치 미분 열도 별도 프로세스에서 계산한다. 실제 적분 단계와 이벤트 처리는 순서대로 진행한다. `run_underbody_mission.py`는 기본적으로 계산 작업자 11개와 적분 프로세스 1개를 논리 프로세서 0~11에 배치하고, 각 프로세스의 BLAS 스레드는 1개로 제한한다. 작업자마다 공력표와 Bullet 연결을 따로 갖는다. 접촉·포획·줄 구간 상태를 매 작업에 전달하며, 정상 종료와 예외 모두 작업자를 정리한다. 미분 계산이 필요 없는 구간에서는 12개 프로세서가 항상 바쁘지는 않다.

## 전개 정체 수정과 전 과정 재계산

중단 상태에서 와이어 위치를 수 나노미터 바꾸자 포획부 곡면의 최근접 삼각형이 바뀌면서 접촉 법선이 갑자기 달라졌다. 가장 가까운 면 하나만 고르는 방식이 다각형으로 표현한 내부 곡면의 경계에서 힘의 불연속을 만들었다. `capsule_mesh(..., skin=...)`는 인접 삼각형마다 연속적인 최근접점을 구하고, 접촉 영역 가장자리에서 0이 되는 가중치로 힘을 나눠 받도록 수정했다. 전체 형상의 간격 검사, 관통 중단 기준, 접촉 강성·감쇠·마찰과 포획 조건은 유지했다. 접촉 힘의 수치 모델을 수정한 것이므로 과거 궤적을 같은 모델의 새 전체 결과로 이어 붙이지 않는다.

`runs/integrator_parallel_01`에서는 기존 접촉식과 작업자 11개로 45초 동안 시뮬레이션 시간이 약 0.000821초 진행했다. 수정 후 `integrator_manifold_01`은 0.01초를 약 10.22초에 완료했다. 서로 다른 길이의 국소 시험이며 전체 임무의 속도 향상률이나 완료 시간을 보증하지 않는다. 허용오차를 4배 엄격하게 한 `integrator_manifold_tight_01`과 같은 종료 시각을 비교하면 센서 위치 차이는 약 4.3e-14m, 최대 와이어 위치 차이는 약 2.3e-9m였다. 이 짧은 구간 검사로 전체 임무 수렴을 판정하지 않는다.

`tests/test_parallel_contact.py`는 곡면 조각 경계에서 힘의 연속성, 평면 접촉, 실제 H1 공력·CAD에 대한 병렬/직렬 힘과 미분 계산 일치, 활성 줄 구간·포획 상태 전달, 작업자 정리를 검사한다. 기존 접촉·포획·운동량·에너지 검사와 함께 확인했다. 명령 생성 함수를 가져올 때 과거 해석 코드 경로가 삽입되던 문제도 수정해, 새 작업자가 해당 실행에 보존된 코드만 불러오게 했다.

`runs/funnel_mission_02`는 수정 코드를 보존하고 새 수납 트림에서 0초부터 시작한다. 실제 정밀 flow5 공력표, 와이어 2.7m, 완전 전개 유지 60초, 기존 회수·포획·문 닫힘 순서를 사용한다. `progress.html`에서 계산된 시각을 확인한다. 최종 완료 여부는 `completion_status.json`과 `complete/verification.json`을 확인해야 하며, 실행 시작만으로 전체 영상이 완성됐다고 판단하지 않는다.
